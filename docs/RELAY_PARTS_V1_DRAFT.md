# MAVKA Relay Content Parts V1

Узгодження Android ↔ ПК. Прийнято назву й поля пропозиції ПК.
Контракт стосується транспорту; чинні формати документів, AES, підписів Relay та ACK не змінюються.

## Рівні пакування
1. Взяти точні UTF-8 байти **оригінального зашифрованого JSON**, без повторної серіалізації.
2. Розділити їх на блоки по **12000 байтів**; останній може бути коротшим.
3. Кожну частину JSON нижче зашифрувати чинним `MAVKA_ENCRYPTED_V1` (AES-256-GCM).
4. Надіслати цей зовнішній AES-конверт через наявний підписаний Relay API.

```json
{
  "format": "MAVKA_RELAY_CONTENT_PART_V1",
  "clientId": "<ClientId профілю Android>",
  "transferId": "0123456789abcdef0123456789abcdef",
  "index": 0,
  "count": 2,
  "size": 12001,
  "sha256": "<64 lowercase hex>",
  "data": "<standard Base64>"
}
```

| Поле | Правило |
| --- | --- |
| clientId | Точний ClientId погодженого профілю; той самий в обох напрямках |
| transferId | Нові 16 випадкових байтів у 32 lowercase hex; стабільний для повторного надсилання цієї передачі |
| index | Ціле від 0 до count − 1 |
| count | Ціле, точно ceil(size / 12000) |
| size | Додатне ціле: повна кількість UTF-8 байтів оригінального зашифрованого JSON |
| sha256 | SHA-256 тих самих повних байтів, 64 lowercase hex |
| data | Канонічний стандартний Base64 з padding; після декодування точно 12000 байтів, крім останнього блока |

## Приймання й повтори
- Спочатку перевірити підпис довіреного відправника й маршрут Relay, розшифрувати зовнішній AES-конверт, перевірити clientId та поля частини.
- Об'єднувати тільки частини одного довіреного відправника/одержувача, clientId і transferId. count, size та sha256 мусять збігатися.
- Частини можуть надходити в довільному порядку. Однаковий index з однаковими байтами — повтор; з іншими байтами — конфлікт.
- Зберігати частини захищено на пристрої. ACK окремої частини дозволено лише після надійного збереження і перевірного читання; він не означає завершення передачі чи затвердження документа.
- Після отримання всіх частин скласти байти за index, перевірити точний size і sha256, строго декодувати UTF-8 та перевірити JSON.
- Лише після цього розшифрувати оригінальний конверт і виконати чинну перевірку документа/файла. Не вносити неповний документ в облік.
- Повтор після мережевої помилки зберігає transferId, байти частин та Relay messageId. Нове шифрування не є повтором старого пакета.
- Стан збору не прив'язувати до короткого терміну життя окремого серверного пакета. Не видаляти вже ACK-нуті частини через неповну передачу.

## Межі реалізації Android
Початкова реалізація обмежує одну збирану передачу 6 000 000 байтами (500 частин),
а захищену локальну чергу — 32 МБ. Більші файли й надалі діляться чинним файловим
протоколом на окремі зашифровані JSON-пакети, кожен з яких можна передати цим способом.
Перевищення межі відхиляється до ACK; формат wire від цього не змінюється.

Малі повідомлення можна надсилати без частин у чинному зовнішньому AES-конверті,
якщо вони вкладаються в ліміти Relay. Не використовувати назви MAVKA_RELAY_PART_V1
або поле totalBytes: погоджено MAVKA_RELAY_CONTENT_PART_V1 і size.
