# MaVka Relay — Cloudflare Workers + D1

Серверний API для `mavka-relay.arudichik.workers.dev`.
База: **наявна** `mavka-messages`; прив'язка Worker: **DB**.
Google OAuth відкладено. Користувацькі дані передаються у зашифрованих
`MAVKA_ENCRYPTED_V1` пакетах. Сервер не отримує ключів AES або приватних ключів пристроїв.

Ця зміна готує сервер та інструменти перевірки. Підключення транспорту до
інтерфейсів Android і ГОЛОВНОЇ МАВКИ потребує окремої клієнтської інтеграції.
Злиття PR саме по собі не означає готовність клієнтів або дозвіл на запуск.

## Перевірка локально

Потрібен Node.js 24+. Із папки `relay`:

```bash
npm ci --ignore-scripts
npm run check
npm run check-bundle
```

Тести запускають справжній локальний `workerd`/Miniflare та D1 на синтетичних
ключах і даних. `check-bundle` збирає Worker через Wrangler `--dry-run` з тимчасовою
конфігурацією. У цих командах немає змін робочого Worker чи віддаленої бази.
Версії Wrangler і Miniflare та їх залежності зафіксовано в `package-lock.json`.

## Модель довіри і реєстрація

1. На стороні головної Мавки створюється окрема пара **ECDSA P-256** для підпису
   Relay-запитів. Приватний ключ має залишатися у сховищі Windows. Серверу потрібні
   лише ID головного пристрою та публічний JWK. Це окрема пара від ключів AES обміну.
2. Публічний ключ головної Мавки закріплюється у конфігурації Worker.
   Відкритої реєстрації, пароля адміністратора за замовчуванням або спільного
   токена, зашитого в APK, немає.
3. `POST /v1/bootstrap` має бути підписаний саме закріпленим ключем. Він одноразово
   створює головний пристрій. Повторний ідентичний запит безпечний; інший ключ
   шифрування для того самого ID не замінює попередній.
4. Мобільний пристрій генерує власні ключі ECDSA/ECDH P-256 в Android Keystore.
   Через довірене спарювання головна Мавка одержує його ID та публічні ключі.
   Наявний Gmail/QR HMAC не містить цих нових ключів: формат спарювання слід доповнити
   під час клієнтської інтеграції. Не довіряти ключу з неперевіреного повідомлення.
5. Головна Мавка підписує `POST /v1/devices`. Пристрій стає `pending`.
   Його `POST /v1/devices/activate`, підписаний власним ключем, переводить його в `active`.
6. Головна Мавка може відкликати мобільний пристрій. Відкликаний ID не реєструється
   повторно й не активується знову. Для нового спарювання потрібні новий ID і ключі.

`public_encryption_key` зберігає публічний ECDH-ключ для клієнтського спарювання.
Сам Relay не обчислює спільний секрет, не розшифровує пакети й не роздає ключі AES.
Головна Мавка та мобільний пристрій мають зберігати довірений публічний ключ співрозмовника.
Ключ, просто отриманий від Relay, не є самостійним доказом довіри.

## API

Усі маршрути обмежені Україною за **довіреним `request.cf.country`**.
Заголовок `CF-IPCountry` від клієнта не використовується. Невизначена країна
також відхиляється. Це фільтр IP-геолокації: VPN/проксі може змінити видиму країну,
тому він доповнює криптографічну авторизацію.
API призначене для нативних клієнтів: браузерні запити з `Origin` відхиляються.

| Метод і маршрут | Доступ / результат |
|---|---|
| `GET /health` | Без підпису; лише назва, версія, стан виконання; не перевіряє готовність D1 |
| `POST /v1/bootstrap` | Закріплений ключ головного пристрою; тіло `{publicEncryptionKey}` |
| `GET /v1/status` | Головна Мавка; готовність D1 і лічильники |
| `POST /v1/devices` | Головна Мавка; `{deviceId,publicSigningKey,publicEncryptionKey}` |
| `GET /v1/devices?after=ID` | Головна Мавка; до 50 записів та курсор `next` |
| `POST /v1/devices/activate` | Запрошений пристрій; тіло `{}` |
| `POST /v1/devices/ID/revoke` | Головна Мавка; тіло `{}` |
| `POST /v1/messages` | Активний відправник; головна ↔ мобільна Мавка |
| `GET /v1/messages?limit=10` | Власна черга активного отримувача; до 50 пакетів, приблизно 256 KiB |
| `POST /v1/messages/ID/ack` | Лише отримувач; `{payloadSha256}`; атомарне підтвердження і видалення |

Для продовження перегляду черги використати `afterTime` і `afterId` з поля `next`.
Для наступного циклу синхронізації починати без курсора, щоб повторно отримати
непідтверджені пакети. Читання черги нічого не видаляє.

Тіло надсилання (тільки ці поля):

```json
{
  "messageId": "унікальний UUID або ID довжиною 16–80 символів",
  "recipientDeviceId": "ID отримувача",
  "expiresAt": 1792340000,
  "payload": {
    "format": "MAVKA_ENCRYPTED_V1",
    "algorithm": "AES-256-GCM",
    "keyId": "0123456789abcdef",
    "nonce": "12 байтів у стандартному Base64",
    "ciphertext": "шифротекст у стандартному Base64",
    "tag": "16 байтів у стандартному Base64"
  }
}
```

Приклад описує структуру; текстові підказки не є валідним тестовим пакетом.
Час — Unix UTC у секундах. Строк зберігання задає клієнт: від поточного часу
до 7 діб. Максимальний шифротекст одного пакета — 32768 байтів, HTTP-тіло — 49152 байти.
Великі файли клієнт ділить на окремі зашифровані частини. Відкриті документи,
імена, підрозділи або теми листів в API-пакет не додаються.

Повторне надсилання з тим самим `messageId` та ідентичними нормалізованими даними
повертає `queued` або `delivered`, а не створює другий пакет. Змінений вміст
з тим самим ID дає `409 message_id_conflict`.

## Підпис кожного запиту

Заголовки:

- `X-Mavka-Device`: ID пристрою; дозволено `A-Z a-z 0-9 _ -`, 16–80 символів.
- `X-Mavka-Time`: Unix UTC у секундах, десять десяткових цифр.
- `X-Mavka-Nonce`: випадкові 16 байтів у Base64url без `=`.
- `X-Mavka-Signature`: ECDSA P-256 / SHA-256, **64 байти IEEE P1363 (`r || s`)**,
  Base64url без `=`. ASN.1 DER не використовується.
- `Content-Type: application/json` для POST; GET має порожнє тіло.

Підписується UTF-8 такого рядка, без останнього переносу:

```text
MAVKA_RELAY_REQUEST_V1
https://mavka-relay.arudichik.workers.dev
POST
/v1/messages
DEVICE_ID
UNIX_SECONDS
NONCE_BASE64URL
LOWERCASE_HEX_SHA256_OF_EXACT_BODY_BYTES
```

Origin, метод, повний шлях **разом із query string** і точні байти тіла є частиною
підпису. Для GET SHA-256 обчислюється від порожнього рядка. JSON не серіалізувати
повторно після підписання. Дозволене відхилення годинника ±300 секунд.
Nonce зберігається в D1 до кінця всього вікна придатності підпису, включно
з підписами з майбутнім часом. Перезапуск Worker не скидає захист від повтору.
Повтор транспортної спроби використовує новий nonce; `messageId` зберігається.
Для .NET використати `DSASignatureFormat.IeeeP1363FixedFieldConcatenation`.

## Що саме означає ACK і видалення

Отримувач спершу перевіряє збережений підпис відправника з довіреним ключем,
ID отримувача, ID пакета, строк та `payloadSha256`. Допоміжна реалізація —
`verifyDelivery` у `src/protocol.js`. Підпис доставки може бути старшим за 5 хвилин:
перевірка часу запиту виконана під час приймання сервером, а строк доставки — `expiresAt`.

Далі клієнт перевіряє AES-GCM, **надійно записує** повідомлення/частину в локальне
сховище з унікальним `messageId` і лише тоді надсилає підписаний ACK.
ACK означає збереження на пристрої, а не прочитання користувачем чи затвердження накладної.
Для файлів кожна частина має бути збережена до свого ACK; відновлення після збою
не повинно втрачати вже підтверджені серверу частини.

`payloadSha256` — SHA-256 від нормалізованого JSON об'єкта у такому порядку полів:
`senderDeviceId`, `messageId`, `recipientDeviceId`, `expiresAt`, `payload`;
у `payload` порядок: `format`, `algorithm`, `keyId`, `nonce`, `ciphertext`, `tag`.
JSON без зайвих пробілів та без екранування `+`, `/`, `=`; усі значення цього об'єкта — ASCII.
Для .NET потрібен сумісний режим `JavaScriptEncoder.UnsafeRelaxedJsonEscaping`.
Функція `fingerprint`
є еталонною реалізацією.

У D1 в одній транзакції записується ACK і виконується `DELETE` зашифрованого пакета.
Якщо видалення не вдалося, ACK також відкочується. Повторний ACK безпечний.
Якщо відповідь на ACK загубилася, нове надсилання початкового пакета поверне
`delivered` без відновлення шифротексту в черзі.

Службовий запис містить лише ID, хеш і час підтвердження; зберігається до початкового
`expiresAt + 24 години`, після чого очищається. Унікальні ID повідомлень не слід
використовувати повторно навіть після очищення. При відкликанні пристрою його
пакети стають недоступні, а непідтверджені зашифровані дані очищаються за строком.
Cron кожні 5 хвилин прибирає прострочені пакети, nonce, лічильники та службові записи.

Видалення стосується активної бази й API-черги. Історичні копії D1 / Time Travel
підпорядковуються строкам Cloudflare; Worker не може гарантувати негайне фізичне
стирання шифротексту з усіх резервних копій провайдера.

Ліміти: 500 пристроїв включно з відкликаними, 10000 пакетів загалом,
1000 у черзі одного відправника/отримувача; 120 запитів за хвилину на мобільний
пристрій, 300 на головний, 3000 загалом. Ліміти черги перевіряються всередині
операції вставки. Порожні/відкликані ключі або відсутня конфігурація блокують доступ.

## Підготовка Cloudflare Builds

Поточний стан, підтверджений скриншотом: репозиторій `arudichik-source/Mavka-Android`,
гілка `main`, **Disable builds увімкнено**. Залишити так до завершення перевірки.

Після підготовки реальної ідентичності головної Мавки потрібні три **публічні**
параметри Build variables (не приватні ключі і не ключ AES):

| Змінна | Значення |
|---|---|
| `MAVKA_D1_DATABASE_ID` | UUID вже створеної бази `mavka-messages` з її Overview |
| `MAVKA_ADMIN_DEVICE_ID` | ID головної Мавки, яка володіє приватним ключем підпису |
| `MAVKA_ADMIN_SIGNING_JWK` | Публічний JWK ECDSA P-256 головної Мавки, без `d` |

`npm run configure` перевіряє параметри й створює локальний `wrangler.json`.
Він закріплює DB і публічний ключ головного пристрою. Відсутні/некоректні параметри
зупиняють збірку; нова база автоматично не створюється.

| Налаштування Builds | Значення після підготовки коду |
|---|---|
| Root directory | `relay` |
| Build command | `npm run configure` |
| Deploy command | `npx wrangler versions upload` |
| Enable Preview builds | Вимкнено |
| Build watch paths | Тільки `relay/**` (щоб Android-зміни не запускали Relay) |

Production version URLs вимкнено (`preview_urls: false`). Команда upload завантажує
версію, але не робить її активним Worker. Cron і робочий маршрут також потрібно
застосувати при погодженому випуску. Не змінювати Deploy command на `deploy`
без окремого погодження користувача.

## Дії лише після погодження розгортання

Перед виконанням звірити live-схему: `PRAGMA table_info(devices);`
і `PRAGMA table_info(messages);`. Основні колонки наведені у міграції.
18.10.2026 колонки підтверджено скриншотами користувача: ключ шифрування
може бути NULL у старих записах, статус за замовчуванням — `pending`.
Нова реєстрація через API вимагає обидва валідні публічні ключі.
Робочу базу не замінювати; міграція додає службові таблиці та індекси.
Якщо у базі є старі діагностичні записи, їхню долю вирішити окремо:
непідписані старі пакети не адаптуються автоматично й не видаються через нову чергу.

Після користувацького погодження, з налаштованим локальним Wrangler:

```bash
npx wrangler d1 migrations apply mavka-messages --remote
npx wrangler deploy
```

Ці дві команди змінюють сервер. Вони **не** виконуються тестами або CI.
Далі виконати справжній підписаний bootstrap із головної Мавки, зареєструвати
синтетичний мобільний пристрій та перевірити повний цикл із мережі України.
Клієнтські приватні ключі, AES-ключі й Cloudflare API token у Git не записуються.

## Локальний клієнт для синтетичного QA

### Реальна ідентичність головної Мавки на Windows

`tools/Initialize-RelayAdmin.ps1` використовує Windows CNG поточного користувача,
ECDSA/ECDH P-256 та політику `CngExportPolicies.None`. Приватні ключі не записуються
в JSON і не передаються в Cloudflare. Публічні параметри зберігаються в
`%LOCALAPPDATA%\MaVka\Relay\admin-public.json`.

На тому ПК й у тому Windows-акаунті, де працюватиме ГОЛОВНА МАВКА, після
перегляду скрипта виконати з папки `relay` у Windows PowerShell 5.1:

```powershell
.\tools\Initialize-RelayAdmin.ps1 -Initialize -DatabaseId <UUID_ІСНУЮЧОЇ_D1>
```

Цей режим працює локально й виводить три публічні значення для Build variables.
Повторний запуск використовує ту саму ідентичність і перевіряє відповідність
метаданих ключам у Windows; іншу базу або підміну публічного ключа відхиляє.
Для повторного перегляду параметрів: `-ShowConfiguration`.
Не видаляти сховище Windows-ключів: перенесення головної Мавки на інший ПК
потребуватиме окремого переприв'язування кореневого ключа в Cloudflare.
Скрипт не змінює політики виконання PowerShell.

Після погодженого розгортання з цим публічним ключем:

```powershell
.\tools\Initialize-RelayAdmin.ps1 -Bootstrap
.\tools\Initialize-RelayAdmin.ps1 -Status
```

Тільки ці два явно вибрані режими звертаються до фіксованої HTTPS-адреси Relay.
`-Bootstrap` реєструє головний пристрій, `-Status` надсилає підписаний запит до стану.
Редиректи не дозволені. Кнопки в інтерфейсі ГОЛОВНОЇ МАВКИ ще потрібно підключити
до цієї ідентичності та протоколу; наявність скрипта не означає готової UI-інтеграції.

У Windows CI `-SelfTest` створює окремі синтетичні CNG-ключі, перевіряє заборону
експорту, повторне відкриття та стабільність ідентичності, а потім видаляє лише
власні тестові ключі. Node/Web Crypto перевіряє створений PowerShell-підпис.

### Синтетичний переносний клієнт Node

```bash
node tools/relay-client.mjs keygen <НОВА_ПАПКА_ПОЗА_РЕПОЗИТОРІЄМ>
node tools/relay-client.mjs request <identity.private.json> POST https://mavka-relay.arudichik.workers.dev/v1/bootstrap <bootstrap.public.json>
```

`keygen` відмовляється замінювати існуючу папку. Приватний файл призначений
для синтетичних перевірок на локальному ПК; він не замінює Keystore/DPAPI.
Не встановлювати тестовий публічний ключ як робочий кореневий ключ.
Команда `request` виконує реальний запит до явно заданої адреси; перед запуском
переконатися, що тестовий сервер/ідентичність налаштовані. Вона не розшифровує
пакети й не надсилає ACK автоматично.
